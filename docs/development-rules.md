# 开发、验收与发布规则

根目录[AGENTS.md](../AGENTS.md)是Agent执行入口；本文件补充会话工作流，不能覆盖根规则或用户当前明确指令。

## 任务组织

1. 明确一个功能的目标、范围、约束、验收标准；只读取相关上下文。
2. 检查Git状态、当前分支和已有修改；通常使用独立 `codex/` 分支/工作树及PR。关联Bug不必另开任务。
3. 并行工作明确文件归属、协议与数据影响、合并及部署负责人；不要同时修改同一文件或操作同一构建缓存。
4. 实现、构建、复现原问题并验收修后行为；有未决问题就记录，不用“全部正常”代替证据。
5. 收尾更新状态和关联记录，列出修改位置、实际检查、未完成事项、风险及未提交修改。提交、推送、合并、部署分别遵从当前用户授权；没有授权不自动执行。

不要编辑README.md；不要将其他任务修改、临时探测脚本、存档、密钥及备份混入提交。Git分支不是提交授权，用户聊天也不是存档来源。

## 构建与测试

- 正式Web配套构建入口为 `npm run build`，脚本为 `scripts/build-web.js`；Windows/WSL细节先核对 `scripts/build-wsl.js` 和已有构建说明。不要把临时机器的绝对工具链路径作为通用要求。
- 数据由 `cpp/CMakeLists.txt` 暂存到构建目录data；从完整构建目录运行。修改JSON任何原始字节、地图或tileset都会改变哈希，客户端与服务端必须配套重建。
- 修改消息布局须提高 `cpp/shared/net/protocol.h` 的协议版本；修改头文件、结构体或公共类后重编依赖和入口，不能伪造对象文件时间跳过编译。
- `--copy-only`只复制已有构建，不能代替编译。历史临时增量构建方案不等于通用干净发布流程；正式产物必须能追溯到对应源码。
- dist受版本控制，`.bin`与原文件必须一致移动，解压后逐字节相同。`.gitattributes`保持产物原始字节，防止Windows换行转换破坏一致性。
- 优先复现用户具体场景并验证实际服务端结果。C++用例可用 `FLIX_TEST_FILTER=<名称片段>` 运行，但零测试不是通过；重编后确认运行的是新二进制。
- 浏览器自动化与实体iPad测试不同，绘制指令减少与真机FPS提升不同，短时并发与长期容量保证不同。报告明确环境、数量、持续时间和限制。

## 生产部署

仅在有明确部署授权后使用 `scripts/deploy-with-backup.cjs`，禁止直接覆盖线上文件或先迁移再备份。

1. 部署前设置 `FLORR_DEPLOY_ADMIN_FILE` 指向仓库外的私密JSON，字段为 `username`、`password`、当前线上 `protocolVersion`、`contentHash`；可选 `url`，默认 `ws://154.219.105.161:8088/ws`。使用具有数据库admin标志的专用运维账号，避免挤掉玩家正在使用的管理员会话；不能按用户名授予权限。当前线上版本/哈希须核实，不能填候选新版本。凭据不得入Git或日志。
2. `deploy-with-backup.cjs`自动发送120秒、60秒、30秒、10秒全服Admin公告，收到服务器同账号同内容的Admin频道回传后才继续倒计时。鉴权失败、版本不匹配、连接断开、公告未确认都中止，不能绕过广播直接停服。恢复预估统一写“预计几十秒后恢复，完成检查后开放。”，不要写“预计几分钟”。
3. 首次运维账号配置例外：用户明确授权自行配置、存档不存在任何正式管理员时，可显式设置 `FLORR_BOOTSTRAP_DEPLOY_ADMIN=1` 与 `FLORR_PRESERVE_SAVE=1`。本次无法发送游戏内公告，须事先说明；先展示维护页60秒，停服并完成备份校验后只新增随机密码运维账号。现有账号逐字段不变，候选在恢复入口前验证实际管理员登录和公告回传。以后部署仍必须先广播。
4. 倒计时结束后启用本次中文维护等待页和小游戏，确认玩家不会看到502。
5. 正常停服保存；将停服最新存档下载到 `D:/ashflor/backups/florrclone/<UTC时间>/`。
6. 本地和服务器SHA256完全一致后，才能处理候选存档、迁移、切换正式发布。
   启用 `server.background-save` 的版本还须核对退出进程的最终保存回执，包括 SHA256、文件大小和账号、角色数。新进程成功写出首份存档后才开放入口。
7. 所有账号定向调整及旧商品恢复必须幂等，保护用户更新后进度、主动操作和无关字段；不能重复退款或删除。
8. 验证后端健康、资源、配套协议与内容哈希，再撤维护页、验证公网入口。
9. 记录部署目录、源码/产物提交、备份位置和校验结果；存档及备份不入Git。

同一次维护中由单服修复改为首次集群发布时，可使用 `maintenanceContinuation` 续接已确认的公告；必须验证四次公告日志、原本地与远端备份SHA、当前候选版本、持续关闭的维护门及维护时间。此入口不替代最新停服备份和完整双服验收，也不能用于跳过尚未发送的公告。新增授权物品发放只对SHA已验证的停服候选执行，绑定账号ID并使用幂等标记。

一服当前直连 .158:8088。原 .161:8088 只负责 302 跳转。独立二服 .161:10000 用 `florr-fresh`、`/opt/florr-fresh/current` 和 `/var/lib/florr-fresh/cpp-state/inventory.json`。发布目标文件指定 `instance: "fresh"` 时，维护、停服、备份和验收只针对该进程及 10000 端口。两服的停服备份分开校验。

直通下载可设置 `FLORR_CLIENT_ASSET_MIRROR` 为独立静态资源的 HTTP(S) origin。此项要求 `FLORR_DOWNLOAD_QUEUE=0` 和 `FLORR_CLIENT_ASSET_HOST`。镜像须提前提供候选压缩 WASM 的内容寻址路径，支持匿名跨域和精确字节范围。发布脚本在维护广播前校验完整 SHA256 及 206 响应。页面、游戏连接和存档仍由各自服务提供。

一服发布可用 `FLORR_PASSWORD_RESET_FILE` 指向仓库外的私密 JSON。每项填写实际登录名、核对过的账号 ID 和新密码。脚本校验最新停服备份后生成改密候选，只改目标凭据并清除目标账号的会话，再校验写出的密码散列和远端候选的 SHA256。登录测试使用独立测试档，避免替玩家触发签到。改密更新使用当前存档，不能与恢复旧档或初始化运维账号混用。玩家在线可从「账户」自行修改，管理员可用数据库编辑器重置玩家密码并注销其会话。

## 文档维护

- 默认交接只读四份上下文：当前状态记录“现在是什么、证据在哪、谁负责剩余工作”；架构记录“实现在哪里”；游戏规则记录“必须保持什么”；本文件记录“如何安全实施与发布”。AGENTS.md维护阅读顺序与强制规则。
- 当前分服只记“待完成，由另一个对话接手”，不在默认上下文复制故障排查过程；不得据此当成已完成或混入单服发布。
- 历史部署和排查记录转入按日期命名的归档，保留证据但不列为默认阅读任务。新摘要注明日期及验证边界，避免把长日志重新堆回当前状态。
- 隔离候选发布时记录准确源码目录、协议、内容哈希及产物校验；工作区有其他任务修改时，不以根dist或当前源码替代已发布候选。以当前进度备份和校验为前提处理恢复，不能直接恢复旧进度。

- 架构细节维护 `cpp/docs/ARCHITECTURE.md`；`docs/architecture.md`只做导航。
- 长期游戏约束维护 `docs/game-canon.md`，具体数值留在数据与代码，必要时链接验收记录。
- `docs/current-status.md`保持简短当前摘要，历史细节保留原日期记录，避免每次会话重读全部日志。
- 更改状态时注明依据及日期，不把历史成功检查写成当前持续有效，也不覆盖其他任务进行中的进展。
